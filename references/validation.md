# 对比验证协议

## 验证层次

1. 结构：入口、元数据、配置、路径、资源、导入与引用是否有效。
2. 行为：真实执行两版相同输入，分别断言预期，并比较产物。
3. 语义：模型是否选择了正确分支、保留约束、适当处理错误并完成任务。

结构通过不能推断后两层。辅助脚本仅覆盖确定性的局部检查；
模型行为须用真实代表性请求验证，条件允许时交给独立执行者做前向测试。
没有独立执行者时，说明由当前执行者完成，不伪称独立评测。

## 用例设计

先在实施前确定预期，避免按新结果反向编写“通过”断言。
固定用例计划、输入与参数包并保存摘要，实施后增加的用例作为有理由的补充，
保留原计划和变更记录，不用删减计划隐藏失败。每次运行使用新工作目录。
按实际能力覆盖正常、空/最小/最大边界、非法输入、缺配置/依赖、
路径变化、失败回退与重试。存在隐私、外部副作用或多格式分支时增加针对性用例。

先使用 `prepare_baseline.py` 准备与原目录互不包含的来源副本。
确认 snapshot.json 存在、摘要匹配，并判断 excluded 是否影响运行。
该脚本拒绝链接与特殊文件，保留普通文件、二进制资源和空目录；
敏感文件与配置指定的排除目录不复制，有排除项时 complete=false。
不直接从原目录执行任何基线代码，即使已切换 cwd 或添加 Python -B。
代码仍可能写绝对路径或产生外部副作用，副本不是沙箱；审查后才可运行。
原目录运行前后核对文件集合和摘要，修改只能落在副本及获准工作目录。

来源副本与目标分别使用干净工作目录，固定输入、参数、运行时与依赖版本。
保存命令、退出码、真实产物、断言依据及环境差异。工作记录不要保存密钥值；
请求体含敏感数据时使用获准的脱敏固定样例。

来源也要做独立预期断言，不能只证明两个版本都产生了同一种错误。
来源存在已确认问题时保留失败证据，新版按获准修复的预期做回归测试。

不能执行来源时：报告阻塞；可以评估目标，但不能宣称完成成对等价测试。
不能使用真实服务时：可用桩验证本地逻辑，但保留端到端服务验证缺口。
随机/生成式产物：预先定义结构、内容覆盖、质量和失败处理指标，
执行适量重复评估；不自动删掉差异字段后声称相同。

## 用例计划与记录格式

每个运行目录包含一个 `run.json` 和实际产物。所有产物路径必须位于记录文件
所在目录之内，不能经过符号链接、junction 或 `..`。不同目录下的物理文件名
可以不同，用 `id` 映射逻辑产物。

新建记录使用版本 2，并在实施前固定独立的 `plan.json`：

```json
{
  "schema_version": 1,
  "cases": [
    {
      "id": "normal",
      "execution_kind": "command",
      "input_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "required": true
    }
  ]
}
```

两版各自生成运行记录，例如：

```json
{
  "schema_version": 2,
  "cases": [
    {
      "id": "normal",
      "execution_kind": "command",
      "input_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "status": "executed",
      "exit_code": 0,
      "checks": {"expected_total": true, "expected_schema": true},
      "artifacts": [{"id": "summary", "path": "normal/summary.json", "mode": "json"}]
    }
  ]
}
```

示例 SHA-256 仅展示格式，真实记录必须对同一份包含输入与参数的规范化输入包
计算摘要。使用文件输入时，可将固定输入和参数打包为稳定 JSON，再计算该
JSON 的 UTF-8 字节摘要。两版必须使用相同算法，环境记录另外保存在测试日志。
输入包含机密时不要发布摘要或原文，先换获准的合成数据。

计划的 `id` 唯一，`required` 为布尔值；计划和两版记录的执行类型、输入摘要
必须相符。不适用范围在计划中提前说明理由，不能运行失败后把必需项改为可选。
比较器不能证明计划的固定时间、完整性或记录真实性，须保留独立执行证据。

版本 2 每项记录含唯一 `id`、64 位十六进制 `input_sha256` 和 `execution_kind`：

| execution_kind | 证据与退出码 |
| --- | --- |
| command | 保存实际命令及日志，executed 必须填实际整数 exit_code；不接受布尔值 |
| function | 保存实际函数、参数和结果/异常，不允许 exit_code |
| model | 保存真实请求、响应与判定，不允许为模型任务编造 exit_code |

`status` 使用以下值；即使异常发生在断言之前，也要保留原计划中的记录：

| status | 字段与处理 |
| --- | --- |
| executed | 执行完成，checks 至少一个命名布尔断言，artifacts 为列表；断言可为 false |
| failed | 执行异常或测试程序无法完成；必须有 reason，可不填 checks/artifacts；提供时两者同时提供，命令退出码只在实际获得时填写 |
| blocked | 条件不满足而无法执行；必须有 reason，不填 exit_code/checks/artifacts |
| not-run | 尚未执行；必须有 reason，不填 exit_code/checks/artifacts |
| not-applicable | 不适用；必须有 reason，不填 exit_code/checks/artifacts；仅两版都不适用且计划 required=false 时可从必需验收中排除 |

执行完成不等于检查通过。`checks` 值不接受字符串 `"true"`，比较通过要求
两版检查项相同且全部为 true；实际非零退出码也可能是非法输入用例的正确预期。
产物元素 id 唯一，mode 为 bytes、text 或 json；无文件输出时列表可为空，
但要用实际响应、状态或副作用检查支持断言。失败不能只写日志后从 run.json 删除。

`bytes` 精确比较，`text` 按 UTF-8 解码，仅规范 CRLF/CR 为 LF，
`json` 按严格 JSON 解析，忽略对象键顺序和空白，按下面的数值规则比较；
布尔值与数字不相等，
不接受重复键或 NaN/Infinity，不隐去时间戳或其他业务字段。
JSON 数字 `1` 与 `1.0` 在此工具中也视为不同，若契约允许这种差异应使用
明确的语义断言，而非声称此比较器检查通过。
十进制使用 Decimal 精确比较，不经过二进制 float；同一十进制数的不同写法
如 `1.0`、`1.00`、`1e0` 相等。不同精确值如
`1.00000000000000001` 与 `1.00000000000000002` 不相等，
数组顺序、字段集合和字符串内容仍严格比较。

旧版兼容：schema_version=1 仍支持原来的 executed/blocked 格式，
执行项必须有实际整数 exit_code，适合进程用例；函数和模型新任务改用版本 2。
两版记录的 schema_version 必须一致，不自动迁移历史记录或补造退出码。

## 比较结果

```text
python scripts/compare_runs.py <baseline/run.json> <target/run.json> --plan <plan.json>
```

- 退出 0：result=pass，适用用例满足计划、相同输入与执行类型、实际命令退出码
  一致、检查全通过、指定产物一致，且至少有一个用例通过。
- 退出 1：差异、断言/执行失败、缺少计划用例（包括两边同时漏测）、
  额外用例或未执行；全部不适用时 result=not-applicable，也退出 1。
- 退出 2：计划、记录、文件路径、JSON 或文件读取不合法；版本 2 未提供计划。

版本 2 必须用 --plan；版本 1 可选用计划，否则结果 scope=recorded_cases_only，
只证明已记录部分相符，不证明覆盖完整。带计划时 scope=planned_cases。
JSON 结果包含 result、scope、cases 和 issues；只列用例与产物标识及问题类别，
不回显产物内容。CLI 顶层错误仅列错误类别，避免泄露路径或正文。
它依据记录比较文件，无法证明命令确曾执行、断言充分或契约覆盖完整。
必须保存独立运行证据，不得把填写 manifest 当作测试。

## 交付门槛

报告每项能力的 passed / failed / blocked / not-run，而非一个笼统成功标志。
所有必须用例通过后才能宣称对应范围验证通过；任何未测项单列。
行为变化经批准后使用独立验收断言，不通过人为修改基线掩盖差异。
严格成对比较仅用于等价部分；获准修复的旧失败、新正确预期另列证据，
不为了让比较器通过而把合法差异从产物里删掉。
按 [兼容验收与可分享测试](restructuring.md#运行前提与兼容验收) 检查实际变更；
重要运行代码修复的最小离线回归应从移位后的成果目录独立运行。
提出的优化建议说明预期收益、变更成本、兼容影响、验证方法和是否实施。
